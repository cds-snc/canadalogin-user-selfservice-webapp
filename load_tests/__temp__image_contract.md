# Load Test Image Contract

This document defines the interface between the load testing platform and your load-testing Docker image.

## Overview

To register your application, you must push a docker image from your CI pipeline to an ECR repository that will be created for you. See the [Integration Guide](integration-guide.md) for more details.

This docker image should perform necessary setup, invoke K6 to perform load testing, and then upload the summary JSON to the S3 bucket provided to your image in the ENV variables. The rest of the orchestration process is handled by the system.

## Environment Variables (Inputs)

The platform injects these environment variables into your container at runtime:

| Variable          | Source                 | Description                                                                                                                                                                            |
| ----------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `APP_NAME`        | Task definition        | Your app's registered name (e.g. `profile-management`)                                                                                                                                 |
| `DISPLAY_NAME`    | Task definition        | Human-readable app name (from `display_name` config, falls back to `APP_NAME`)                                                                                                         |
| `LOAD_MULTIPLIER` | Task definition        | Integer scaling factor for load counts. This allows load to be increased independantly from your CI/CD pipeline. Defaults to 1. You should multiply VU numbers by the LOAD_MULTIPLIER. |
| `ARTIFACT_BUCKET` | Task definition        | S3 bucket name for uploading results.                                                                                                                                                  |
| `RUN_ID`          | Step Function override | Timestamp identifying this execution (e.g. `2026-03-19T14:00:00.000Z`). Use this in logs to identify a run.                                                                            |
| `ARTIFACT_PREFIX` | Step Function override | S3 key prefix for this run (e.g. `runs/2026-03-19T14:00:00.000Z/`)                                                                                                                     |

Any additional key/value pairs in your `env_vars` config are also injected as environment variables.

## Secrets

Each app has a dedicated Secrets Manager secret (`gc-signin-staging-load-test-<name>-secrets`). This secret is a JSON object where each key/value pair represents a secret your container needs. The ECS task execution role has permission to read this secret.

To use secrets in your container, read them from Secrets Manager using the AWS SDK at startup:

```sh
# In your entrypoint script, before running K6:
SECRET_JSON=$(aws secretsmanager get-secret-value \
  --secret-id "gc-signin-staging-load-test-${APP_NAME}-secrets" \
  --query SecretString --output text)

# Export individual keys as environment variables
export MY_API_KEY=$(echo "$SECRET_JSON" | python3 -c "import sys,json; print(json.load(sys.stdin)['MY_API_KEY'])")
```

Populate the secret via the AWS Console or CLI after your app is registered in Terraform.

## Required Output

Your container **must** upload two files to S3:

1. **JSON summary** — used by the platform to extract metrics for Slack notifications:

   ```
   s3://${ARTIFACT_BUCKET}/${ARTIFACT_PREFIX}summary.json
   ```

2. **HTML report** — generated by [k6-reporter](https://github.com/benc-uk/k6-reporter), published to CloudFront for viewing:
   ```
   s3://${ARTIFACT_BUCKET}/${ARTIFACT_PREFIX}summary.html
   ```

Both files are produced by K6's `handleSummary` callback. Your test script must export a `handleSummary` function that returns both outputs:

```js
import { htmlReport } from "https://raw.githubusercontent.com/benc-uk/k6-reporter/3.0.4/dist/bundle.js";

export function handleSummary(data) {
  const appName = __ENV.DISPLAY_NAME || __ENV.APP_NAME || "Load Test";
  const date = new Date().toISOString().split("T")[0];
  return {
    "/tmp/summary.html": htmlReport(data, { title: `${appName} — ${date}` }),
    "/tmp/summary.json": JSON.stringify(data),
  };
}
```

## Exit Code

- **Exit 0**: The platform treats this as a successful run and proceeds to process results and send a success Slack notification.
- **Non-zero exit**: The platform sends a failure Slack notification with error details. K6 exits non-zero when thresholds are breached, so a threshold failure will be reported as a failed run.

## Recommended Image Structure

Use a multi-stage Docker build with K6 and the AWS CLI:

```dockerfile
FROM grafana/k6:0.54.0 AS k6
FROM amazon/aws-cli:2.22.35

COPY --from=k6 /usr/bin/k6 /usr/local/bin/k6
COPY test.js /tests/test.js
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh

ENTRYPOINT ["/entrypoint.sh"]
```

Your entrypoint script should:

1. Run K6 (which produces `/tmp/summary.json` and `/tmp/summary.html` via `handleSummary`)
2. **Always** upload both files to S3, even if K6 exits non-zero (threshold breach)
3. Exit with the original K6 exit code

```sh
#!/bin/sh

k6 run /tests/test.js
K6_EXIT=$?

# Always upload — the platform needs both files to generate reports
if [ -f /tmp/summary.json ]; then
  aws s3 cp /tmp/summary.json \
    "s3://${ARTIFACT_BUCKET}/${ARTIFACT_PREFIX}summary.json"
fi
if [ -f /tmp/summary.html ]; then
  aws s3 cp /tmp/summary.html \
    "s3://${ARTIFACT_BUCKET}/${ARTIFACT_PREFIX}summary.html"
fi

exit ${K6_EXIT}
```

**Important:** Do not use `set -e` before the K6 run. K6 exits with code 99 when thresholds are breached — the platform handles this gracefully by still processing the summary and sending a failure notification with full metrics and an HTML report link.

## Required Header

All HTTP requests from your load test **must** include the `X-LOAD-TESTING` header:

```js
http.get("https://app.example.com/api/endpoint", {
  headers: { "X-LOAD-TESTING": "true" },
});
```

The platform's WAF is configured to allow traffic from the load testing VPC only when this header is present. Without it, requests will be blocked by the bot control and anonymous IP WAF rules.

## Optional: Tags and Groups

To get per-endpoint breakdowns in the HTML report, use K6 tags:

```js
import http from "k6/http";

export default function () {
  http.get("https://app.example.com/api/users", {
    headers: { "X-LOAD-TESTING": "true" },
    tags: { name: "GET /api/users" },
  });
  http.get("https://app.example.com/api/posts", {
    headers: { "X-LOAD-TESTING": "true" },
    tags: { name: "GET /api/posts" },
  });
}
```

To get per-group check breakdowns, use K6 `group()`:

```js
import { group, check } from "k6";
import http from "k6/http";

export default function () {
  group("Login Flow", function () {
    const res = http.get("https://app.example.com/login", {
      headers: { "X-LOAD-TESTING": "true" },
    });
    check(res, { "login status 200": (r) => r.status === 200 });
  });
}
```

## Permissions

Your container runs with an IAM task role scoped to your app only:

- **S3**: Read/write access to your app's artifact bucket only. No access to other apps' buckets.
- **Secrets Manager**: Read access to your app's secret (`gc-signin-staging-load-test-<name>-secrets`) only.
- **Network**: Egress to the public internet via HTTPS and DNS.
